> **情報確認日：2026年10月23日（JST）／限定共有**
>
> 本文はPHP Project、Apache Tomcat Security Team、Spring Security、CERT-EU、JPCERT/CCなどの公表情報をもとにしています。**「製品の深刻度」と「自分の環境における対応優先度」は別物**です。脆弱性情報は更新されるため、作業前にリンク先の最新版を確認してください。攻撃手順の再現ではなく、防御と運用判断に焦点を当てています。

2026年10月21日、PHPの**未認証で任意コード実行（RCE）につながる脆弱性2件**の修正版が公開されました。前日20日にはApache TomcatでもHTTP/2のリクエスト・レスポンスがユーザー間で混ざり得る問題が公表されています。

「PHPを使っている担当者だけの話か」と考えかけて、気になったのが**クラウドでアプリケーションを動かしている場合の責任範囲**でした。EC2のOSパッチを適用しても、コンテナイメージやアプリ側の依存ライブラリが古いままなら問題は残ります。

この記事では、最近のPHP・Java系の事例を取り上げながら、公式情報をどう読み、何を調べ、どこまで対処するのかを整理します。

## まず全体像：深刻度・対象・直すバージョン

![公式評価に基づく脆弱性比較図](https://raw.githubusercontent.com/mizzz-ivr/tech-writing/main/assets/security/20261023-vulnerability-severity.svg)

| 対象 / CVE | 公表日 | 公表された指標 | 想定される影響 | 修正バージョン |
| --- | --- | --- | --- | --- |
| PHP / **CVE-2026-109618** | 2026/10/21 | **CVSS v4.0: 9.2（Critical）**。PHP公式・CERT-EU | メモリ処理の不整合によるRCE | **8.2.35 / 8.3.36 / 8.4.27 / 8.5.12**（各系列） |
| PHP / **CVE-2026-109619** | 2026/10/21 | **CVSS v4.0: 9.2（Critical）**。PHP公式・CERT-EU | 古い内部状態の参照によるRCE | 同上 |
| Apache Tomcat / **CVE-2026-101356** | 2026/10/20 | **Important**。Apache Tomcat Security Teamの定性評価 | HTTP/2非同期処理でリクエスト・レスポンス混在 | **9.0.123 / 10.1.61 / 11.0.27** |
| Spring Security / **CVE-2026-47841** | 2026/08/20 | **HIGH**（Spring公式）、**CVSS v3.1: 7.4**（IBM公表、CVSS SourceはVMware） | 一定条件下でWebAuthnのユーザー検証要件を回避 | **7.1.1 / 7.0.7**、旧系列はサポート形態に応じた修正版 |

**注意点：** CVSS v4.0の9.2とCVSS v3.1の7.4を、そのまま大小比較して対応順に並べてはいけません。Apacheの「Important」も独立したベンダー評価です。CVSSは脆弱性の重大性を表す尺度であって、実際の緊急対応期限ではありません。

### なぜ「CVSSだけで判断しない」のか

業務での優先順位には、少なくとも次の4つを合わせます。

1. **製品・バージョンが一致するか**（対象外なら同じ緊急性とは限らない）
2. **脆弱になる設定や機能を実際に使うか**（例：SpringのWebAuthnと分散セッション）
3. **外部から到達できるか**（インターネット公開、認証不要、信頼境界など）
4. **悪用が確認されているか**（CISAのKnown Exploited Vulnerabilities：KEVなど）

「CVSS 9以上だから全環境が即座に侵害される」という意味ではありません。一方、認証不要のRCEが外部公開環境で成立する場合は、CVSSだけを見るまでもなく優先して対処すべきです。

米国CISAの[KEVカタログ](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)は、**実際の悪用が確認された脆弱性**を判断する材料になります。**掲載されていないことは安全の証明ではありません**。参考として旧事例のPHP CVE-2024-4577はKEVに掲載され、IPAも国内での悪用・webshell設置を報告しました。これは**2026年のPHPの2件の悪用確認を意味しません**。

## 1. PHP：CVE-2026-109618 / CVE-2026-109619

PHP公式はこの2件について、**未認証のRCEにつながり得る**として更新を強く推奨しています。環境依存の暫定防御には限界があり、公式のリリース告知は「完全な緩和策はない」と明記しています。

### どのバージョンが対象か

| PHP系列 | 修正が入ったバージョン | 確認ポイント |
| --- | --- | --- |
| 8.5.x | **8.5.12** | 8.5.11以前では更新要 |
| 8.4.x | **8.4.27** | 8.4.26以前では更新要 |
| 8.3.x | **8.3.36** | 8.3.35以前では更新要 |
| 8.2.x | **8.2.35** | 8.2.34以前では更新要。8.2は2026年末にEOL予定 |
| 8.1以前 | 現行のPHP Projectから修正版は提供されない | サポート中の系列への移行計画が必要 |

> ディストリビューションや商用製品では、独自に修正をバックポートしている場合があります。その際は「表示バージョン」だけでなく、**提供元のセキュリティアドバイザリとパッケージの修正履歴**で判断してください。

### そもそもどういう仕組みなのか

![PHPの2件のRCEの概念図](https://raw.githubusercontent.com/mizzz-ivr/tech-writing/main/assets/security/20261023-php-rce-flow.svg)

**CVE-2026-109618：メモリ不足処理（OOM）時の不整合**

PHPが設定されたメモリ上限に達すると、処理を中断することがあります。リクエスト処理の途中に内部データが完全には初期化されていない状態があると、後片付けの際に不正なメモリ操作が起こり得ます。その結果、一定条件では攻撃者が任意コード実行へつなげられる可能性があります。

**CVE-2026-109619：解放済みデータを指す古い内部状態**

異常終了したリクエストで使われていた状態が、メモリの解放後も残るケースが問題です。次のリクエストでその状態が適切に初期化される前に使われると、不正なメモリ参照が発生し、RCEにつながり得ます。

ここで重要なのは、**アプリケーション側の入力チェックだけでは防ぎ切れない場合がある**という点です。PHPランタイム内部で発生するため、アプリのバリデーションを整えていてもアップデートが必要です。

### 放置した場合

脆弱な構成で悪用が成立すると、PHPプロセスの権限でプログラムを実行される恐れがあります。結果として情報窃取、webshellの設置、他のシステムへの侵入の足掛かり化、サービス停止などにつながる可能性があります。**これは起こり得る被害であり、今回の2件ですべての被害が確認されたという意味ではありません。**

### まず何をするか

~~~bash
# このCLIが参照するPHPのバージョン
php -v

# PHPバイナリの場所
command -v php

# 実行中コンテナの棚卸し（Dockerの場合）
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
~~~

**CLIの `php -v` だけで安心しないこと。** Web側のPHP-FPM、mod_php、php-cgi、コンテナ内、別サーバーのPHPは異なるバージョンの場合があります。コンテナイメージのタグだけでなく、実際に稼働しているPHPのバージョンと、イメージの再ビルド・再デプロイの有無も確認します。

運用上は「対象資産の特定 → 修正版の適用 → 正常性確認 → 侵害の兆候の確認」の順番です。更新前から不審なアクセスがある場合は、復旧だけでなく証跡保全・影響調査が必要です。

根拠： [PHP公式のセキュリティ告知](https://www.php.net/archive/2026.php#2026-10-21-5)、[PHP 8.5.12の公式リリース](https://news-web.php.net/php.announce/513)、[CERT-EU](https://cert.europa.eu/publications/security-advisories/2026-018/)、[JPCERT/CC](https://www.jpcert.or.jp/at/2026/at260033.html)

## 2. Tomcat：CVE-2026-101356

PHPのようなRCEとは異なり、こちらは**HTTP/2の非同期Servlet処理において、内部オブジェクトの再利用が不適切になり、ユーザー間でリクエストやレスポンスが混在し得る**問題です。

Apache Tomcat Security Teamの評価は**Important**です。これはApache公式の定性評価であり、CVSSの数値ではありません。

| Tomcat系列 | 影響するバージョン | 修正版 |
| --- | --- | --- |
| 9.0.x | 9.0.118〜9.0.122 | **9.0.123** |
| 10.1.x | 10.1.55〜10.1.60 | **10.1.61** |
| 11.0.x | 11.0.22〜11.0.26 | **11.0.27** |

たとえばある利用者のレスポンス内容が別の利用者に返れば、個人情報の漏えいにつながる可能性があります。**RCEと同一視せず、「別ユーザーへのデータ混入」という実際の不具合の性質**で説明した方が正確です。

### 対処

実際の稼働バージョン、HTTP/2の有効化、非同期Servletの利用を確認したうえで修正版に更新します。ALBでHTTP/2を終端しているからといって、バックエンドまで必ずHTTP/2とは限りません。通信経路のどこでHTTP/2を使っているかを確認し、条件に一致するかを判断します。

JavaアプリをSpring Bootの組み込みTomcatで動かしている場合も対象外とは限りません。Spring Bootが管理する依存関係を調べ、互換性のある修正済みバージョンを選びます。

~~~bash
# Maven: 利用しているTomcatライブラリを確認
./mvnw dependency:tree -Dincludes=org.apache.tomcat

# Gradle: Runtimeの依存関係を確認
./gradlew dependencies --configuration runtimeClasspath
~~~

ソースコードの宣言だけでなく、**本番で動くJARやコンテナに含まれているバージョン**を確認するのがポイントです。

根拠： [Apache Tomcat Security（9）](https://tomcat.apache.org/security-9)、[Apache Tomcat Security（10）](https://tomcat.apache.org/security-10)、[Apache Tomcat Security（11）](https://tomcat.apache.org/security-11)、[Apacheの公開アドバイザリ](https://www.openwall.com/lists/oss-security/2026/10/20/27)

## 3. Spring Security：CVE-2026-47841

Spring Securityが提供する**WebAuthn（パスキー認証などに使用される認証技術）**の実装に関する脆弱性です。

公式評価は**HIGH**。IBMが公開したアドバイザリでは**CVSS v3.1で7.4**、CVSSの評価主体はVMwareとされています。

ただし、**Spring Securityを使っていれば全員が影響するわけではありません**。公式が示す条件は次の3つです。

1. WebAuthnの認証を使う
2. `userVerification = REQUIRED` を明示的に設定する
3. Redis、JDBC、Hazelcastなどの分散HTTPセッションストアを利用する

本来はユーザー検証（PINや生体認証など）を必須にすべき場面で、セッションの直列化・逆直列化後に同一オブジェクト参照かどうかを比べるロジックが問題となります。値の意味は同じでも、参照先が別オブジェクトになり、必須条件が意図せず適用されなくなります。

攻撃条件を満たした場合、**認証器を入手した攻撃者が、本来必要なユーザー検証をせずに認証を完了できる恐れ**があります。パスキー利用者が全員ただちになりすまされる、という意味ではありません。

対象バージョンはSpring Security 6.4.0〜6.4.18、6.5.0〜6.5.11、7.0.0〜7.0.6、7.1.0です。修正版には7.0.7・7.1.1（OSS）や6.4.19・6.5.12（Enterprise Support向け）などがあります。**現在利用可能な修正ルートは系列・サポート契約によって違う**ため、アプリのSpring Bootとの整合性も確認してください。

根拠： [Spring公式 CVE-2026-47841](https://spring.io/security/cve-2026-47841/)、[IBM Security Bulletin](https://www.ibm.com/support/pages/node/7290899)

## 4. AWS・クラウド担当は関係ある？

結論からいうと、**クラウド上で自分たちのアプリケーションを実行しているなら関係があります**。ただし「AWSを契約している＝全部が対象」ではありません。

![AWS上の通信経路と脆弱性対応の責任分担](https://raw.githubusercontent.com/mizzz-ivr/tech-writing/main/assets/security/20261023-aws-defense.svg)

| 環境 | 主に確認すべき対象 | 対応の考え方 |
| --- | --- | --- |
| **EC2** | OS、Webサーバー、PHP/Java、Tomcat、アプリ | OS更新に加えてミドルウェアとランタイムを確認する |
| **ECS / EKS** | コンテナイメージ、ベースイメージ、ライブラリ、稼働タスク/Pod | 脆弱なイメージをビルドし直し、**動いているタスク/Podを更新**する |
| **Lambda** | ランタイムの管理方式、関数コード、同梱ライブラリ、Layer | AWS管理のランタイム部分と利用者が保持する依存関係を区別する |
| **RDS / S3など** | 利用しているサービス機能とアクセス権 | **PHPやTomcatが稼働していないサービス単体**を、アプリのCVEの対象と誤認しない |
| **外部SaaS / マネージド製品** | ベンダーの告知、影響範囲、提供パッチ | 内部コンポーネントを直接更新できない場合、提供元に対応状況を確認する |

ここで誤解しやすいのが「共有責任モデル」です。クラウド事業者が基盤の安全性を担保する範囲と、利用者が設定・OS・コード・データを管理する範囲はサービスによって異なります。

### WAF・セキュリティグループを入れていれば十分？

**十分ではありません。** WAFのルールや非公開化は悪用の可能性を下げる補助策ですが、今回のPHPのようなランタイム内部の問題を完全に解消するものではありません。WAFの導入と脆弱なアプリの修正は、役割の異なる対策です。

AWSではCloudWatch Logs、CloudTrail、GuardDuty、WAFログなどの役割を分けて使います。GuardDutyを有効化しただけで、アプリ内部のすべてのRCEやレスポンス混入を検知できるわけではありません。どのログを取得していて、どの異常を検知できるかまで確認する必要があります。

## 5. いま担当者がやるなら：対応順を決める

以下は**一般的な運用例**であり、政府機関が定めた一律のSLAではありません。実際の期限は脅威情報と自組織の資産・契約・サービス重要度で決めます。

| 優先 | 判断例 | まず行うこと |
| --- | --- | --- |
| P0（最優先） | 外部公開された未修正PHPで該当系列を利用 | 緊急変更を起票。修正版適用、暫定的な露出低減、ログ確認を並行実施 |
| P1（高） | Tomcatの対象版かつ問題となるHTTP/2経路が存在 | 通信経路・依存関係を確認し、修正版へ更新 |
| P1（高） | SpringのWebAuthn・REQUIRED・分散セッション条件が一致 | 利用経路・修正版を確定し、認証機能の回帰テストを優先 |
| 継続管理 | 非公開環境、間接依存、サポート終了ランタイムなど | バージョン・到達性・保有データを確認して対応期限を決定 |

### 更新前後のチェックリスト

- [ ] 本番・検証・待機系を含む資産の棚卸しができている
- [ ] **パッケージの宣言**と**本番で実際に動くバージョン**の両方を確認した
- [ ] CVEの発生条件と公開経路を照合した
- [ ] ベンダー公式の修正バージョン・バックポート情報を照合した
- [ ] ステージングで正常系・異常系・認証系の回帰テストを実施した
- [ ] 本番の再デプロイ後、ランタイム・アプリの稼働版を再確認した
- [ ] 不審なリクエスト、想定外のプロセス、ファイル変更、権限変更などの痕跡を調査した
- [ ] 侵害が疑われる場合、証跡を保全し、隔離・認証情報の再発行・影響範囲調査を行う
- [ ] 問題が発生した場合の切り戻しと復旧手順を用意した

特にTomcatのようなHTTP/2処理の問題は、**通信レイヤー・非同期処理・複数ユーザーの分離**までテスト観点に含める必要があります。Springの問題では、Redis/JDBCを使ったセッションのシリアライズ後にも認証要件が維持されるかを確認します。

## 6. 次の脆弱性で慌てないために

脆弱性情報が出てから毎回「どのチームが見ればいい？」となると、パッチ公開後の初動が遅くなります。

- **資産管理**：SBOM（ソフトウェア部品表）、コンテナイメージ一覧、OS・ランタイムのバージョンを継続的に把握する
- **情報収集**：製品公式アドバイザリ、CISA KEV、JPCERT/CCなどを定期的に確認する
- **CI/CD**：依存関係スキャン・イメージスキャンを実行し、緊急更新用の短いデプロイ経路を用意する
- **防御の多層化**：最小権限、ネットワーク分離、WAF、MFA、ログ監視、バックアップを重ねる
- **運用体制**：脆弱性の一次判定者、修正担当、承認者、インシデント時の連絡先を決める

**「攻撃されない仕組み」を100％保証する方法はありません。** 目標は、脆弱性が見つかったときに対象を素早く特定し、被害を抑え、更新・検知・復旧まで進められる状態です。

今回のPHPのように、**昨日まで問題なく動いていたランタイムでも、翌日には緊急更新が必要になる**。アプリ開発・運用・クラウドの境界で取りこぼさないために、普段のうちから資産と担当範囲を可視化しておきたいところです。
