# 技術記事を書いていたら、「コードの外側」の方が気になってきた

Terraformの設定を書いていたはずなのに、途中で手が止まりました。

「なぜこの構成にしたのか」を書こうとしたら、その先にもう1つ問いがあったからです。

**そもそも、趣味の個人開発を、なぜここまで管理するようになったんだろう。**

Issueを作って、PRを切って、CIを通す。
READMEやRunbookを残して、古いものを整理する。

技術記事なら、やり方は書けます。

GitHub Actionsをどう組んだか。
Terraformをどう直したか。
エラーをどう潰したか。

でも、その手順の途中に「なぜそこまでするのか」を入れようとすると、急に記事の温度が変わります。

コードの話をしていたはずなのに、いつの間にか自分の価値観の話になっている。

技術記事を書き始めたことで、逆に**技術記事では書きにくいこと**が見えるようになりました。

それが、noteを書いてみようと思った最初の理由です。

## 最初は、動けばそれでよかった

個人開発を始めた頃は、もっと単純でした。

作りたいものを思いつく。

書く。

動く。

嬉しい。

次を作る。

それで十分でした。

自分しか触らないRepositoryなら、細かい管理もいらない。
今日書いたコードの理由くらい、今日の自分は覚えています。

でも、projectが増えて、数か月、数年と続くものが出てくると、少しずつ景色が変わりました。

久しぶりに開いたRepositoryで、昔のIssueを見る。

「これ、まだ必要だっけ」

途中のbranchを見る。

「何をしようとしていたんだっけ」

新しい技術を試したくなる。

でも、今の構成はちゃんと動いている。

作ることより、**選ぶこと**が増えていきました。

何を先に作るのか。
何を今は作らないのか。
どこまでやれば十分なのか。
どこから先は、ただ複雑にしているだけなのか。

以前なら「コードを書いていない時間」だと思っていた時間が、だんだん開発の中心に寄ってきました。

## AIで速くなったら、迷わなくなると思っていた

AIを開発に使うようになって、実装はかなり速くなりました。

実装案を出してもらう。
テストを書いてもらう。
エラーを一緒に追う。
知らない技術の入口を作ってもらう。

以前より短い時間で、動くところまで辿り着けることが増えました。

最初は、速くなれば迷う時間も減ると思っていました。

でも、実際は逆でした。

候補が早く出るから、選ぶ回数が増える。

実装できるからこそ、**本当に実装するべきか**を考える。

動いたからこそ、**このまま半年後も直せるか**を考える。

AIがコードを書いてくれても、最後に「これでいい」と決めるところまでは消えませんでした。

むしろ、コードを書く時間が短くなったぶん、前後にある判断がよく見えるようになりました。

最近、自分が面白いと思っているのはそこです。

## 書きたいのは、コードの差分だけじゃなかった

Gitにはコードの差分が残ります。

PRには、何を変えたかが残ります。

Issueには、そのとき何を直そうとしていたかが残ります。

でも、

「なぜその技術を選んだのか」

「なぜ途中でやめたのか」

「AIを使うようになって、自分の仕事をどう考えるようになったのか」

みたいな変化は、意識して残さないと消えていきます。

数か月後の自分は、今の自分が何を迷っていたかをたぶん覚えていません。

だから、完成した答えを書くというより、**その時点の自分の考えをcommitしておく場所**が欲しくなりました。

noteは、自分にとってそんな場所になりそうです。

## 同じ出来事でも、見たい場所が違う

QiitaやZennをやめるわけではありません。

むしろ、技術記事を書き続けたいから分けます。

| 場所 | 自分が書きたいこと |
| --- | --- |
| Qiita | 実装・検証・トラブルシュート。「どうやったか」 |
| Zenn | 設計・Trade-off・内部構造。「技術的になぜそうしたか」 |
| note | 経験・判断・価値観。「自分はなぜそう考えたか」 |

例えば、趣味の個人開発でIssueやPR、CIまで使っている話。

技術記事なら、workflowや設定を書けます。

でもnoteで書きたいのは、その一歩手前です。

**1人しかいないのに、なぜわざわざ止まる場所を作るようになったのか。**

同じ出来事でも、そこから見えるものは違います。

## 正解を書く場所にはしない

ここで何かの正解を教えるつもりはありません。

今の自分が「これがいい」と思っていても、半年後には違うことを言っているかもしれません。

むしろ、それでいいと思っています。

コードなら、考えが変わったら新しいcommitを積みます。

自分の考え方も、たぶん同じです。

昔のcommitが間違いだったから消す、ではなく、そこから何が変わったかが履歴になる。

noteには、そんな**エンジニアとしてのchange log**を残したいです。

AIでコードを書くようになって何が変わったのか。
完成しない個人開発とどう付き合うのか。
仕事と個人開発と勉強の間で、何を残して何を諦めるのか。
技術が変わったとき、自分の価値観はどこまで変わるのか。

すぐ答えが出ないものほど、書いてみたいと思っています。

## あのとき止まったところから書いていく

技術記事を書いていて、手が止まりました。

手順は書ける。

設定も書ける。

でも、その奥にある「なぜ」は、別の記事になりそうでした。

以前なら、そこは脱線として消していたかもしれません。

これからは、消さずに残してみます。

数年後に読み返したとき、

「この頃は、こんなところで立ち止まっていたのか」

と分かるように。

コードの外側にあったものも、自分にとってはちゃんと開発の一部だったと分かるように。
