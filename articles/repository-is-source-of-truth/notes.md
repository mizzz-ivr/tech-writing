# Notes: Repository is the Source of Truth

記事本文に入れる前の事実確認・体験メモです。

## 記事の中心にしたい話

- AIに次の機能候補を考えさせるだけだと、過去の会話や古いIssueを前提に判断することがある
- 実装済みの機能を候補として出してしまうことがあった
- そこで「Repository is the Source of Truth」を開発エージェントの最重要原則にした
- 現在状態を長いプロンプトに固定するより、毎回Repositoryから再構築させる方が長期の個人開発では扱いやすかった
- GitHubだけですべてを管理するのではなく、Issue / PR / Docs / Notion / 会話にもそれぞれ役割がある

## 公開前にHertaで再確認する内容

- [ ] Reminder Pluginの現在のコマンドと再試行・復旧設計

## 使えそうな具体例

### 既存機能をもう一度作りそうになった

Poll / Reminderなど。「追加すると便利そう」と考える前にRepositoryを検索したら、すでにかなり実装されていた。

記事では機能一覧を大量に並べるより、「自分で作っておいて忘れていた」という出来事を中心にする。

### Issueと実装のズレ

Issueのチェック状態だけでは現在地点を判断できないケースがあった。

記事公開時には、実際にまだ再現できる例かを最新Repositoryで確認してから書く。

### 次タスクの選定

AIに単に「次は何を作る？」と聞くのではなく、Repository、Issue、PR、Docs、Tests、Security、UXなどを確認して次タスクを選ばせる運用へ変えた。

## 書きすぎないこと

- Hertaの内部アーキテクチャ説明だけの記事にしない
- プロンプト全文を貼るだけの記事にしない
- AI万能論にしない
- すべてのチーム開発に同じ方法が正解だと断定しない
- 実装数や効果を根拠なく数字で盛らない

## 記事の読者イメージ

AIでコードを書いている人だけではなく、以下の人も読めるようにする。

- GitHubを使って個人開発している人
- 複数のプロジェクトを並行している人
- 久しぶりに触るRepositoryの現在地点を思い出すのが大変な人
- AIエージェントをどこまで任せていいか迷っている人
