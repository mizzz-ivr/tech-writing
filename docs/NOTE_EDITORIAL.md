# note Editorial Strategy

## 目的

noteはQiita / Zennの代替ではなく、**エンジニアとして何を考え、どう判断し、どう生きているか**を発信する媒体として使う。

技術の説明そのものより、実際の開発・仕事・学習・社会との接点から生まれた経験、判断、価値観を中心に書く。

## 媒体の役割

| 媒体 | 主な役割 | 主な問い |
| --- | --- | --- |
| Qiita | 実装・検証・問題解決 | How: どう実装・解決したか |
| Zenn | 設計・技術深掘り | Design / Why technically: なぜその設計にしたか |
| note | 経験・思想・キャリア・社会 | Why personally / What I think: なぜそう考えるか |

同じ開発経験を複数媒体で扱うことは許容するが、**同一本文の重複投稿はしない**。媒体ごとに答える問いを変える。

### 例

- Qiita: AI開発エージェントをRepository is the Source of Truthで動かす方法
- Zenn: AI Runtimeの安全境界、Quota、Kill Switch、Provider abstractionの設計
- note: AIにコードを書かせるようになって、エンジニアとしての役割をどう考えるようになったか

## noteの4本柱

### 1. エンジニアとしての考え方

技術そのものではなく、技術者としての判断軸や価値観を書く。

候補:
- 個人開発を何年も続ける理由
- 「完成させる」より「作り続ける」ことを大事にしている理由
- AIでコードを書くようになって、エンジニアに必要な能力はどう変わったか
- コードを書く時間が減ってもエンジニアと言えるのか
- 個人開発でPR / Issue / CIまで使うのはやりすぎなのか
- 技術選定で「一番新しい技術」を選ばなくなった理由

### 2. 個人開発の裏側

完成した実装ではなく、そこへ至る迷い・失敗・運用・継続の難しさを書く。

候補:
- 個人開発を複数抱えると、コードを書くより管理の方が難しくなってきた
- 趣味なのにGitHub ProjectsやNotionで管理する理由
- 個人開発を止めないために、あえてやらないことを決めている
- OSSを作る側になって分かったこと

### 3. キャリア・仕事・学習

転職ノウハウの一般論ではなく、自分がどう判断したかを中心にする。

候補:
- 技術者として成長できる会社とは何か
- 年収だけで転職先を決めない理由
- 「設計ができる人」より「実装できる人」でいたいと思う理由
- スペシャリストを目指すという選択
- 本業と個人開発を両立して分かったこと
- 資格勉強と個人開発、どちらへ時間を使うか
- GitHubをPortfolioとして育てるようになって変わったこと

### 4. 技術 × 経済・社会

エンジニアの視点から、AI・労働・経済・教育・所有・プラットフォームなどを考える。

候補:
- AIでソフトウェア開発の価値は下がるのか
- 個人開発者がAIによって一人企業に近づいている
- SaaSを作るコストはどこまで下がるのか
- OSSはなぜ無料なのに成立するのか
- GitHubはエンジニアの履歴書になっていくのか
- AI時代にプログラミングを学ぶ意味はあるのか
- クラウド時代なのに自宅サーバーを持つ意味
- 巨大プラットフォームと個人開発者は共存できるのか

## 投稿ペース

- 目安: **月1本程度**
- 年12本を埋めること自体を目的にしない
- 実体験や考えが十分に溜まった題材を優先する
- 技術記事の投稿頻度とは切り離す

年間の目安:
- 技術思想・個人開発: 4本
- キャリア・仕事: 3本
- AI・社会・経済: 3本
- 技術以外: 2本

これはノルマではなく、偏りを確認するための目安とする。

## 最初の6本

1. 技術記事とは別に、エンジニアとして考えていることを書く場所を作ることにした
2. 個人開発を「完成させること」より「続けること」を大事にしている
3. AIにコードを書かせるようになって、エンジニアの仕事について考えた
4. 趣味の個人開発なのにIssue・PR・CIまで使う理由
5. 技術者として「何を知っているか」より「どう判断するか」が大事になってきた
6. AIで一人の開発者が作れるものはどこまで増えるのか

第1回は自己紹介を兼ね、Qiita / Zenn / noteの役割分担と、noteで何を書いていくかを明示する。

## 有料記事の方針

初期は無料記事を優先する。有料化を投稿開始の目的にはしない。

### 無料記事

- 思想
- 体験
- 問題提起
- 判断に至った背景
- 読むだけで一つの結論まで到達できる内容

### 有料記事

無料部分だけでも価値があり、その上で次のような**実用的な追加価値**を提供できる場合に検討する。

- 再現可能なノウハウ
- 判断フレームワーク
- 実際に使っているテンプレート
- 比較表や評価基準
- 運用手順
- 長期間の実体験から整理した具体策

「結論だけ隠して続きを読むために課金する」構成にはしない。

候補例:
- 個人開発を継続するための実際の管理・運用テンプレート
- AI開発を運用するためのルールと判断基準
- GitHub Portfolio構築の実践ガイド
- エンジニア転職の比較・判断フレームワーク
- 個人サービスのインフラ設計とコスト判断

## 執筆ルール

- 一般論を断定するより、自分の経験と観測範囲を明示する
- 技術的な事実を含む場合はSource of TruthとなるRepository / Docsを確認する
- 他社・顧客・非公開プロジェクトの機密情報を書かない
- 転職や仕事の体験を書く場合も、個人・企業を不必要に特定できる情報は避ける
- 経済・社会テーマでは事実と意見を分ける
- 数字・制度・時事情報を扱う場合は公開前に最新情報を確認する
- Qiita / Zennで既に書いた内容を、そのまま文章だけ柔らかくして再投稿しない

## Writing Analyticsとの関係

現時点のWriting AnalyticsはQiita / Zennの外部reaction取得を対象としている。noteはまず編集方針と記事企画に組み込み、外部reaction取得は安定した取得方法を確認できるまで実装前提にしない。

noteの公開URL・公開履歴をAnalyticsへ正式対応する変更は、editorial方針とは分離して実装する。

## 目指す状態

`tech-writing`を単なる技術記事置き場ではなく、次の両方を示せる発信基盤にする。

- **Technical Portfolio**: 何を実装・設計・検証できるか
- **Thinking Portfolio**: 何を経験し、どう考え、どう判断する人なのか
