# note Storytelling Guide

note記事は、結論や主張を先に説明するだけの文章にせず、**読者が出来事を追いながら考えの変化へ辿り着ける構成**を優先する。

## 基本構造

原則として次の順を使う。

1. **場面** — 実際に手が止まった、迷った、気づいた瞬間から始める
2. **違和感** — なぜその出来事が引っかかったのかを書く
3. **過去** — 以前はどう考えていたかを短く戻る
4. **変化** — 経験や環境の変化で考え方がどう変わったかを書く
5. **今の考え** — 一般論ではなく、現在の自分がどこに立っているかを示す
6. **余韻** — 冒頭の場面や言葉を最後に回収する

## 書き方

- 「この記事では〜を説明します」から始めない
- 最初の数段落で、具体的な場面・違和感・問いのどれかを置く
- 結論を最初に全部言わず、読者が途中で意味を理解できる順序にする
- 箇条書きや分類は必要なところだけに使い、本文の主役にしない
- 一般論を長く続けず、自分の経験 → 自分の解釈の順で書く
- 短い段落を使ってテンポを作るが、意図のない一文改行を連発しない
- 技術用語は残してよいが、技術解説だけで物語を止めない
- 成功談だけにせず、「以前はこう思っていた」「途中で考えが変わった」を残す
- 読者を教える対象として扱うより、一緒に出来事を振り返る距離感を優先する

## noteで避ける構成

- 冒頭から媒体方針や結論を一覧で説明する
- 「理由は3つあります」だけで全編を進める
- Qiita / Zenn記事を柔らかい口調にしただけの再投稿
- 実体験のない一般論だけを並べる
- すべてを綺麗な成功談へ整えすぎる
- 読者に対して断定的に「こうすべき」と結論づける

## 技術記事との違い

同じ出来事を扱う場合でも、問いを分ける。

- **Qiita:** どう実装・解決したか
- **Zenn:** 技術的になぜその設計にしたか
- **note:** その経験で自分の考えがどう変わったか

noteでは技術的な事実を背景として使ってよい。ただし、設定値や手順そのものより、**その出来事の前後で何を考えるようになったか**を中心にする。

## レビュー時の確認

公開前に最低限、次を確認する。

- 冒頭に続きを読みたくなる具体的な場面があるか
- 最初の段階で結論を全部説明していないか
- 「以前の自分」と「今の自分」の差が見えるか
- 抽象論だけでなく、変化のきっかけになる出来事があるか
- 章ごとに同じ主張を言い換えて繰り返していないか
- 最後が単なる要約ではなく、冒頭や中心テーマを回収しているか
- Qiita / Zennと同じ記事になっていないか

このガイドは文章を文学的にするためではなく、**経験と判断を読み物として伝えるため**に使う。
